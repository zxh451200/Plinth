# 升级与版本回退

本说明描述当前源码的处理规则。正式交付前仍需执行 Windows 安装、真实 EF 迁移和恢复演练；没有运行结果的步骤不能记为验收通过。

## 当前格式

| 内容 | 当前版本 | 兼容规则 |
|---|---|---|
| 工程版本 | 0.1.0，待发布 | 由 Directory.Build.props 统一定义 |
| 数据库迁移 | InitialSchema → NotesEntries → CodeIdentityKeys | 向前升级，未知或较新迁移拒绝打开 |
| 用户设置 | SchemaVersion 2 | 接受 1 并升级；缺少 Region / TimeZoneId 时跟随系统 |
| ZIP 备份 | FormatVersion 1 | 校验 manifest、白名单、SHA-256 和数据库结构 |
| 工作区布局 | Version 1 | 旧 ZIP 无工作区文件时恢复默认布局 |

地区和时区字段仍属于 schema 2 的可选追加字段。空字符串跟随系统；导入的无效地区按 invariant 格式显示，无效或不可用的显式时区回退 UTC。设置页只提交有效的新选择。设置不会改变原有 UTC 数据，也不转换无时区的业务日期。

编码键迁移支持应用默认创建的 UTF-8 SQLite 库。外部创建的 UTF-16 库会在初始化检查或直接执行迁移时被拒绝，不能用错误字节回填 CodeKey；原库需要保留并另外安排数据迁移。历史编码原文不在升级时 Trim。输入保存／导入仍沿用去首尾空白规则，因此人为写入旧库的带首尾空白编码，不保证 CSV／XLSX 导出再导入仍命中同一行，操作前应单独核对。

## 升级操作

1. 用旧版应用完成保存并创建 ZIP 备份，复制到程序目录和数据目录之外。记录旧安装包、版本、数据目录，以及单独管理的 branding.json 和 deployment.json。备份不包含部署身份配置或系统凭据。
2. 完全退出应用后替换程序文件或运行安装器，保留原用户数据目录。不要通过删除 plinth.db 或设置文件来“修复”升级。
3. 新版启动检查数据库迁移和实际结构。新库执行全部迁移；已知六列旧库先补审计字段并建立 InitialSchema 基线，再依次补 NotesEntries 和 CodeIdentityKeys。编码键迁移重建两个模块表，保留原编码、ID、版本和审计值，回填 CodeKey 并以其建立唯一索引。升级在候选副本上执行，成功后才替换原库，安全副本保留在原目录。
4. 核对地区时间显示、窗口与工作区布局，以及备份创建和恢复。若部署启用了 `IncludeSampleModules`，再核对示例数据和便笺保存。身份部署还需验证登录和实际权限。

保存中的设置会在关闭前等待完成。保存失败会保留窗口并定位设置页，原已提交设置继续生效；查看错误后再次关闭可以退出。

备份页现有“确认备份并安全退出以便升级”入口：选择目标、核对预览后执行，只有备份成功且页面未离开时才请求主窗口退出。退出仍经过未保存确认及后台任务收尾；拒绝退出会保留已完成的备份，失败、取消或备份中离页不会自动退出。

该 ZIP 是创建一致性快照时已保存数据的备份，不包含退出确认中才保存的修改或快照之后的写入。需要完整的升级前最终状态时，应先保存业务修改、等待写入任务结束，再创建备份；如果取消退出后继续修改，应重新备份。它不启动安装器、不绕过安装锁，也不等同于安装器自动备份。新增入口及真实窗口回归尚需在 Windows 上执行验收。

安装器固定使用当前用户的 `%LOCALAPPDATA%\Programs\Plinth`。`/D=` 不能改到其他目录，也不从卸载注册表读取删除目标；目录链接会被拒绝。已有安装在交互确认后优先调用旧版受控命令创建 ZIP。历史版不支持命令、自动备份失败或旧 EXE 缺失时，可选择此前由旧应用备份页创建的 ZIP；取消选择会停止安装。安装包中的新版助手必须验证自动生成或手选的 ZIP，展示应用版本、schema、UTC 创建时间、文件数及解压后总大小，再由用户确认后才能覆盖。校验、授权、助手启动或占用检查失败返回 6，没有“忽略失败继续”入口。静默首次安装可用，静默升级仍一律拒绝并返回 6。

受控命令形状为 `Plinth.App.exe --backup-before-upgrade <绝对 ZIP 路径>`，必须单独使用，成功返回 0，参数错误返回 2，备份失败返回 8。它通过现有 `BackupService.BackupToAsync` 执行权限和生产确认检查，使用 SQLite Backup API（包含已提交 WAL 数据）、设置白名单、SHA-256 manifest 和不覆盖发布，发布后再次校验完整 ZIP；不迁移原库、不应用待恢复内容、不下载脚本、不裸复制 db/WAL。

新增只校验命令为 `Plinth.App.exe --inspect-backup-before-upgrade <绝对 ZIP 路径> <助手目录内的新报告文件绝对路径>`，返回码同上。它通过 `BackupService.Inspect` 校验 manifest、文件白名单、大小、SHA-256、数据库完整性、迁移兼容性及清单 schema 一致性，仅临时解压 ZIP，不打开或迁移当前数据库，不创建备份或准备恢复。报告使用 UTF-16LE，包含经过长度和控制字符限制的备份摘要，禁止覆盖已有报告。校验仍执行 `backup:export` 授权和生产确认，且拒绝服务器数据库配置。认证部署没有登录会话、Production 没有生产确认回调时，两种命令都拒绝，不提供跳过权限或确认参数；这些部署需另行安排受控升级流程，手选 ZIP 不能绕过限制。

备份保留在 `%LOCALAPPDATA%\Plinth-Upgrade-Backups`，名称由系统生成并追加 `.zip`；现有目标绝不覆盖，失败后可能已发布的 ZIP 也保留。命令拒绝程序目录或数据目录内目标，以及数据库／目标路径上的目录链接。安装器继承的 `PLINTH_DATA_DIR` 必须与待升级数据一致；它只备份这个目录，不自动发现其他便携数据目录。开始前应在提示中核对默认目录，使用其他目录时从设置了相同环境变量的终端启动安装器，分别保管其他数据目录的备份。

安装目录独占锁贯穿备份和覆盖。启动旧版命令时暂时关闭旧 EXE 写句柄（否则 Windows 无法加载它），子进程退出后重新取得写句柄，检查通过才开始覆盖。普通新实例仍被目录锁阻止；自动备份命令另外占用与桌面相同的数据目录互斥量，遇到已有实例失败且不唤醒窗口。旧 EXE 缺失的修复安装跳过旧程序调用及其句柄重取，但仍须验证 ZIP；卸载信息或已有交付锁也作为修复安装标记。

助手由安装包完整发布目录（含 .NET 运行时、托管与本机依赖）解压至 NSIS 的 `$PLUGINSDIR` 私有临时目录后运行，不覆盖安装目录，不使用旧目录 DLL，不需要旧版实现新增命令。临时工作目录也指向助手目录；安装器继承环境变量，并将既有 `deployment.json` 复制到助手目录，拒绝配置链接、目录、不可读或复制失败，保留原部署策略。NSIS 退出时清理临时目录。此方案增加一次完整解压的时间和临时磁盘占用，但避免单独维护另一套备份实现和依赖裁剪清单。文件选择使用标准 `nsDialogs::SelectFileDialog open`（取消返回空字符串），报告通过 `FileReadUTF16LE` 读取。

清单和哈希只能证明备份内容有效，无法证明它属于当前数据目录或包含最近写入。确认框明确要求核对来源和时间；修复前已有 ZIP 同样需核对，快照之后的修改应重新备份。真实 Windows 调用、文件选择/取消、HEAD 历史版升级、缺 EXE 修复、锁竞争、安装器在磁盘满下的故障恢复演练尚未执行（应用启动与 CLI 备份的磁盘满行为已单独实测，见 [实现状态](IMPLEMENTATION_STATUS.md)），Linux 源码检查或 NSIS 编译不能替代这些验收。

Windows 应用启动后持有安装目录 `plinth.install.lock` 的只读共享句柄，直到退出。不同数据目录的多个实例可以共享；安装／卸载需要独占访问，所以必须退出同一程序目录启动的所有实例。安装期间启动应用会提示文件不可用并返回 3，尚未打开数据。`--version` 不取得安装锁。该文件是随包交付的程序资源，请勿手动删除；它不存储用户状态。

安装器还检查旧 EXE 的写占用，拒绝覆盖运行中的旧版本，不强杀进程或安排重启覆盖。升级时将旧 EXE 移到安装目录的独立临时路径后再解包，成功后删除本次临时文件。失败时保留用户数据和可能的旧 EXE，移除启动所需的锁文件，让新版本拒绝打开未完成安装；请重新运行完整安装包。此过程不是整包原子替换，不提供自动回滚，磁盘满／断电／杀进程仍需 Windows 故障演练。

卸载按当前发布包生成的明确文件清单删除程序，仅对空目录执行非递归移除；未知文件、用户放入的 ZIP、自定义数据及旧版本残留文件保留。遇到已知子目录被改成链接时停止，不沿链接删除内容。卸载后安装目录可能仍存在，不应为了清理残留而手动递归删除整个目录。正常数据仍应放在系统用户数据目录，不建议把 `PLINTH_DATA_DIR` 指到安装目录。

## 升级失败

数据库迁移失败时，原数据库不执行迁移；保留的 `.before-migrate-*` 安全副本及 `.error` 文件用于定位。若程序报告未知结构或更新的迁移，请使用匹配版本检查数据，不手工修改迁移历史表。

恢复 ZIP 时，程序先校验和准备候选，下次启动才应用。替换前保留数据库与设置的安全副本，恢复中断时使用事务记录回滚。若回滚副本缺失或回滚失败，程序停止启动并保留记录；不要删除记录强行启动。日志可能包含本机路径，分享前核对内容。

## 回退到旧版

数据库不自动降级。只认识 InitialSchema／NotesEntries 的旧版会拒绝已经包含 CodeIdentityKeys 的数据库；新迁移也明确拒绝执行反向 DDL。不能只换回旧 EXE，或删除迁移历史伪装旧库。

回退应在完全退出后恢复**升级前的匹配数据和配置快照**，再使用对应旧程序。推荐先在独立数据目录验证：通过 `PLINTH_DATA_DIR` 指向新的空目录，使用旧版恢复它能识别的升级前 ZIP。不要让新旧程序同时访问同一个数据目录。

升级后新增的便笺和其他修改不会出现在升级前备份中。需要保留时先人工导出或记录，并明确接受回退的数据时间点。数据库安全副本可能不包含同一时刻的设置，不能随意拼接为恢复集合。
